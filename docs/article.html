Weather apps tell you everything, every day. A daily forecast notification trains you to swipe it away, so on the one morning it says "−25°C tonight" or "70% chance of rain", you've already stopped reading.

I wanted the opposite: silence, unless something I care about is about to happen. You set a rule like "rain chance ≥ 60%" or "low ≤ −10°C" and get an email at 7 a.m. only on the days that rule is crossed. Every other day, nothing.

This tutorial builds that, end to end, as a small serverless app you can deploy into your own AWS account in about half an hour. I deployed it, tested it with a real inbox, hit three real problems, and redesigned part of it after community feedback. All of that is written up below.

What you'll walk away with

  • A public signup API: POST /subscriptions with an email, a city and a rule
  • Double opt-in and unsubscribe links without writing a single line of email code
  • A 7 a.m. scheduled job (in your timezone, daylight-saving safe) that alerts only the people whose rule triggered
  • Production habits: retries, dead-letter queues, idempotency, abuse limits, least-privilege IAM, encryption
  • A verify checklist with real outputs, and a one-command clean up

STEP 2Write the alert rules as pure logic

Everything that decides "should we alert?" lives in one file with no AWS calls. That way the code most likely to have bugs is tested in milliseconds, before anything is deployed.

// src/rules.mjs
export const RULES = {
  rain:  { label: 'Rain', unit: '%',  min: 1,   max: 100, field: 'precipitation_probability_max', ... },
  snow:  { label: 'Snow', unit: 'cm', min: 0.1, max: 200, field: 'snowfall_sum', ... },
  below: { label: 'Cold', unit: '°C', min: -60, max: 50,  field: 'temperature_2m_min', ... },
  above: { label: 'Heat', unit: '°C', min: -30, max: 60,  field: 'temperature_2m_max', ... },
  wind:  { label: 'Wind', unit: 'km/h', min: 1, max: 300, field: 'wind_speed_10m_max', ... },
}

export function evaluate(rule, daily, dayIndex = 0) {
  const def = RULES[rule.type]
  const value = daily?.[def.field]?.[dayIndex]
  if (typeof value !== 'number') return { triggered: false, value: null } // missing data never alerts
  const triggered = rule.type === 'below' ? value <= rule.threshold : value >= rule.threshold
  return { triggered, value }
}
Design choiceIf the weather API returns null, the safe failure is silence, not an email that says "null°C". Adding a new rule type is a single line: pick an Open-Meteo field and a comparison.

STEP 3Get weather data with no API key

// src/weather.mjs
async function getJson(url, timeoutMs = 5000) {
  const res = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) })   // never hang
  if (!res.ok) throw new Error(`HTTP ${res.status} from ${new URL(url).host}`)
  return res.json()
}

export async function getDailyForecast(latitude, longitude) {
  const params = new URLSearchParams({
    latitude: String(latitude), longitude: String(longitude),
    daily: DAILY_FIELDS.join(','),
    timezone: 'auto',          // "today" means today where the city is
    forecast_days: '1',
  })
  const data = await getJson(`https://api.open-meteo.com/v1/forecast?${params}`)
  if (!data.daily) throw new Error('Forecast response had no daily block')
  return data.daily
}

Two details that matter in production: always put a timeout on fetch (otherwise a hanging third-party API eats your whole Lambda timeout, and your money), and use timezone: 'auto' so the daily values match the city's local calendar day, not UTC. You can try it before touching AWS:

STEP 4Subscribing: let SNS do the email work

The trick that keeps this project small: one SNS topic for everyone, and a filter policy on each email subscription so it only receives messages tagged with its own ID.

// src/subscribe.mjs (core)
const id = randomUUID()

const sub = await sns.send(new SubscribeCommand({
  TopicArn: TOPIC_ARN,
  Protocol: 'email',
  Endpoint: email,
  Attributes: { FilterPolicy: JSON.stringify({ subscriptionId: [id] }) },
  ReturnSubscriptionArn: true,
}))

await ddb.send(new PutCommand({
  TableName: TABLE_NAME,
  Item: { id, email, ...place, rule: { type: rule.type, threshold: rule.threshold },
          // keys for the ByCheckHour GSI the daily job queries (Step 5)
          checkHour: '07', locKey: locKey(place.latitude, place.longitude, id),
          snsSubscriptionArn: sub.SubscriptionArn, createdAt: new Date().toISOString() },
}))

✅ Free: double opt-in

SNS emails "Subscription Confirmation", and nothing is delivered until the person clicks it. Nobody can sign someone else up for alerts.

✅ Free: unsubscribe

Every alert email has an unsubscribe link at the bottom. No unsubscribe endpoint, token or page to build.

Protecting a public endpoint

This endpoint has no login, and every successful call makes AWS send an email to an address the caller chose. That's an abuse vector, so there are three layers of defence:

// 1. Validate everything
if (!EMAIL_RE.test(email)) return json(400, { error: 'A valid email is required' })
if (!city || city.length > 80) return json(400, { error: 'city is required (max 80 characters)' })

// 2. Cap subscriptions per address (GSI query, COUNT only, so it's cheap)
const existing = await ddb.send(new QueryCommand({
  TableName: TABLE_NAME, IndexName: 'ByEmail',
  KeyConditionExpression: 'email = :e', ExpressionAttributeValues: { ':e': email },
  Select: 'COUNT',
}))
if ((existing.Count ?? 0) >= MAX_PER_EMAIL) return json(429, { error: `This email already has ${MAX_PER_EMAIL} alerts` })

// 3. API Gateway throttling: 2 req/s, burst 5 (in template.yaml)

STEP 5The daily job: fast, polite and retry-safe

The job must not read the whole table every morning. Every subscription carries two extra attributes that feed a global secondary index:

GSI ByCheckHourExampleAnswers
Partition key checkHour"07"Which subscriptions are due at this hour?
Sort key locKey"51.05,-114.09#b780…"Sorted by location (~1 km), then id
// src/check.mjs (core)
async function loadDueSubscriptions(checkHour) {
  const items = []
  let ExclusiveStartKey
  do {
    const page = await ddb.send(new QueryCommand({
      TableName: TABLE_NAME, IndexName: 'ByCheckHour',
      KeyConditionExpression: 'checkHour = :h', ExpressionAttributeValues: { ':h': checkHour },
      ExclusiveStartKey,
    }))
    items.push(...(page.Items ?? []))
    ExclusiveStartKey = page.LastEvaluatedKey
  } while (ExclusiveStartKey)
  return items
}

export const handler = async (event = {}) => {
  const checkHour = toCheckHour(event.checkHour ?? DEFAULT_CHECK_HOUR)   // "07"
  const subs = await loadDueSubscriptions(checkHour)   // only what's due
  const groups = groupSorted(subs)                      // already sorted by city → one pass
  const stats = { checkHour, subscriptions: subs.length, locations: groups.length, sent: 0, ... }

  for (let i = 0; i < groups.length; i += CONCURRENCY) {      // 5 at a time
    await Promise.all(groups.slice(i, i + CONCURRENCY).map(async (g) => {
      let daily
      try { daily = await getDailyForecast(g.latitude, g.longitude) }
      catch { stats.failed += g.subs.length; return }
      for (const sub of g.subs) {
        try { stats[await alertOne(sub, daily)]++ } catch { stats.failed++ }
      }
    }))
  }
  if (stats.failed > 0) throw new Error(`${stats.failed} alert(s) failed`)   // → Lambda retries
  return stats
}
// src/keys.mjs: items arrive sorted by locKey, so same-city items are adjacent
export function groupSorted(subs) {
  const groups = []
  for (const s of subs) {
    const cell = s.locKey.slice(0, s.locKey.indexOf('#'))
    const last = groups[groups.length - 1]
    if (last && last.cell === cell) last.subs.push(s)
    else groups.push({ cell, latitude: s.latitude, longitude: s.longitude, subs: [s] })
  }
  return groups
}

Idempotency: why retries don't double-email anyone

async function alertOne(sub, daily) {
  const forecastDate = daily.time?.[0]
  if (sub.lastAlertDate === forecastDate) return 'already_sent'   // ← the whole trick

  const { triggered, value } = evaluate(sub.rule, daily)
  if (!triggered) return 'not_triggered'

  await sns.send(new PublishCommand({ TopicArn: TOPIC_ARN, Subject: subject, Message: message,
    MessageAttributes: { subscriptionId: { DataType: 'String', StringValue: sub.id } } }))
  await ddb.send(new UpdateCommand({ TableName: TABLE_NAME, Key: { id: sub.id },
    UpdateExpression: 'SET lastAlertDate = :d', ExpressionAttributeValues: { ':d': forecastDate } }))
  return 'sent'
}

STEP 6The infrastructure in one SAM template

The full template.yaml is in the repo. These are the parts worth understanding:

SubscriptionsTable:
  Type: AWS::DynamoDB::Table
  Properties:
    BillingMode: PAY_PER_REQUEST
    AttributeDefinitions:
      - { AttributeName: id, AttributeType: S }
      - { AttributeName: email, AttributeType: S }
      - { AttributeName: checkHour, AttributeType: S }
      - { AttributeName: locKey, AttributeType: S }
    KeySchema: [{ AttributeName: id, KeyType: HASH }]
    GlobalSecondaryIndexes:
      - IndexName: ByCheckHour                 # daily job: Query, not Scan
        KeySchema:
          - { AttributeName: checkHour, KeyType: HASH }
          - { AttributeName: locKey, KeyType: RANGE }
        Projection: { ProjectionType: ALL }    # job needs the whole item
      - IndexName: ByEmail                     # signup: per-email cap
        KeySchema: [{ AttributeName: email, KeyType: HASH }]
        Projection: { ProjectionType: KEYS_ONLY }   # only counts, keep it small
CheckFunction:
  Type: AWS::Serverless::Function
  Properties:
    Handler: check.handler
    Timeout: 300
    Policies:
      - DynamoDBCrudPolicy: { TableName: !Ref SubscriptionsTable }
      - SNSPublishMessagePolicy: { TopicName: !GetAtt AlertsTopic.TopicName }
    # Layer 2: if YOUR CODE throws
    EventInvokeConfig:
      MaximumRetryAttempts: 2
      MaximumEventAgeInSeconds: 3600
      DestinationConfig: { OnFailure: { Type: SQS } }
    Events:
      DailyCheck:
        Type: ScheduleV2
        Properties:
          Name: !Sub ${AWS::StackName}-daily-check          # see Real snag #2
          ScheduleExpression: cron(0 7 * * ? *)
          ScheduleExpressionTimezone: America/Edmonton
          # Layer 1: if Scheduler can't DELIVER the invocation
          RetryPolicy: { MaximumRetryAttempts: 3, MaximumEventAgeInSeconds: 3600 }
          DeadLetterConfig: { Type: SQS }

🔐 Least-privilege IAM

The subscribe function can call sns:Subscribe but can't publish. The check function can publish but can't subscribe anyone. Each gets CRUD on only its own table.

🔒 Encryption by default

The table stores email addresses, so it has SSEEnabled and point-in-time recovery turned on. The SNS topic uses the AWS-managed KMS key alias/aws/sns.

Real snag #2: the schedule name that would collideMy first deploy went through cleanly. Then I listed my schedules and saw CheckFunctionDailyCheck. Without an explicit name, SAM names the schedule after the function and event, with no stack name, and schedule names must be unique within a group. A second copy of this stack in the same account (dev + prod, or a reader deploying twice) would fail. The fix is one line: Name: !Sub ${AWS::StackName}-daily-check. On redeploy, CloudFormation created the new schedule and deleted the old one.

💬 What I changed after community feedback

I shared a first draft in the contest Slack. The first comment was blunt and correct:

"Never like seeing a DynamoDB Scan; it looks simple to avoid in this use case (GSI and/or secondary records with a transacted write)."

My v1 daily job did Scan → group in memory → check. A Scan reads every item, every day: the cost grows with the table, not the work (unsubscribed rows included), it reads at most 1 MB per page, one page after another, and I was sorting into cities in memory when the database could do it. In v1 I'd written "Scan is fine to tens of thousands of rows". That was me defending a shortcut, not a design.

OptionHowWhy I did / didn't pick it
GSI ByCheckHour ✅Each subscription gets checkHour + locKey; DynamoDB maintains the index.No extra writes in my code, nothing to keep in sync, and the Query returns items already grouped by location.
Secondary location records + TransactWriteItemsWrite LOC#<cell> / SUB#<id> items in the same transaction as the subscription.Also correct, but every create, update and delete must keep two records in sync, and transactions cost 2× per write.

Bonus: with checkHour as the partition key, letting people choose their own alert hour is now a small change to the signup API plus an hourly schedule, not a redesign.

Real snag #3: CloudFormation finished before the index didI deployed the GSI and the new Query code together. sam deploy printed UPDATE_COMPLETE in 55 seconds. I invoked the job right away and got:
ValidationException: Cannot read from backfilling global secondary index: ByCheckHour
CloudFormation reports success when a GSI is created, not when it's readable. DynamoDB keeps filling ("backfilling") the index in the background, and Queries fail until it's ACTIVE.
right after UPDATE_COMPLETE
$ aws dynamodb describe-table --table-name <SubscriptionsTableName> \
    --query "Table.GlobalSecondaryIndexes[].[IndexName,IndexStatus]"
ByEmail      ACTIVE
ByCheckHour  CREATING     ← CloudFormation already said "complete"

🚦 Add a GSI to a live table in two deploys

1. Deploy the GSI, but keep the old code.
2. Backfill existing rows, then wait for ACTIVE.
3. Deploy the code that queries it.

🔁 Backfill old rows once

Rows written before the change lack checkHour/locKey, so the index can't see them. I set them with a conditional update (attribute_not_exists(checkHour)), which is safe to re-run. A one-time migration is the one place a Scan is fine.

📈 Scaling and limits (the honest version)

Hot partition at huge scale

All 7 a.m. subscriptions share one GSI partition key. At millions, split it into shards (07#0 … 07#9) and Query them in parallel; enqueue location groups to SQS to stay under Lambda's 15-minute limit.

SNS email isn't a newsletter

It's built for notifications. For branded HTML emails or high volume, switch to Amazon SES with a verified domain.

Unsubscribed rows linger

SNS stops delivering to people who unsubscribe, but the job still evaluates their rows. A weekly cleanup could check GetSubscriptionAttributes and delete the dead ones.

One alert time (for now)

The GSI is already keyed by hour. Per-user times just need an hour field on signup and an hourly schedule that queries the current hour.

🎓 What I learned

  1. EventBridge Scheduler beats scheduled rules for anything a human sees, because it handles timezones and daylight saving.
  2. SNS filter policies turn one topic into per-user delivery, and you get double opt-in and unsubscribe links without writing email code.
  3. Asynchronous invocations have two retry layers. Scheduler's retry policy won't catch errors thrown by your own code; Lambda's EventInvokeConfig will.
  4. Retries need idempotency. One lastAlertDate field made "retry the whole job" safe.
  5. Design the table around the question you ask every day. "Who's due now, grouped by city?" is a GSI Query, not a Scan. A reader spotted it in one sentence.
  6. CloudFormation's "complete" isn't DynamoDB's "ready". Add a GSI, wait for ACTIVE, then ship the code that reads it.
  7. Check what your framework named things. A default name with no stack prefix works fine until the day you deploy a second copy.
